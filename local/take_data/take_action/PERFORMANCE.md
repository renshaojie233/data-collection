## 端到端延迟分解

### 延迟组成

```
总延迟 = ROS2发布延迟 + 序列化延迟 + 网络传输延迟 + 反序列化延迟
```

**详细分析：**

1. **ROS2发布延迟**: 1-5 ms
   - 话题订阅回调触发时间
   - 取决于ROS2系统负载

2. **JSON序列化**: 0.1-0.5 ms
   - Python json.dumps() 非常快
   - 数据量小，影响可忽略

3. **网络传输**: 0.5 ms (实测)
   - TCP传输
   - 局域网，延迟稳定

4. **TCP缓冲**: 0-2 ms
   - Socket发送/接收缓冲
   - 通常很小

5. **JSON反序列化**: 0.1-0.5 ms
   - Python json.loads()
   - 影响可忽略

**预期总延迟**: **5-10 ms**

## 性能优化建议

### 当前设计（已实现）

✅ **优点：**
- JSON格式，调试友好
- 实现简单
- 跨平台兼容
- 延迟已经很低（<10ms）

### 如果需要极致性能

可以考虑以下优化（**当前不需要**）：

1. **使用二进制协议**
   - Protocol Buffers / MessagePack
   - 减少50-70%数据量
   - 序列化速度提升3-5倍

2. **UDP代替TCP**
   - 延迟降低2-3ms
   - 但可能丢包

3. **数据压缩**
   - gzip压缩
   - 减少带宽
   - 但增加CPU和延迟

4. **直接ROS2桥接**
   - 使用ros2 bridge
   - 零序列化开销
   - 但需要本地也装ROS2

## 实际场景分析

### 机器人控制频率对比

| 系统 | 控制频率 | 可接受延迟 |
|------|----------|------------|
| Franka FR3 控制器 | 1000 Hz | < 1 ms |
| GELLO → Franka | ~100 Hz | < 10 ms |
| **本系统（数据记录）** | **50-100 Hz** | **< 20 ms** ✅ |

### 为什么延迟不是问题？

1. **非实时控制路径**
   ```
   GELLO → FR3控制器 → 机械臂  (实时，1000Hz)
              ↓
         数据记录系统         (非实时，100Hz)
   ```

2. **数据记录不影响控制**
   - 数据记录是旁路监听
   - 不在控制回路中
   - 延迟10-20ms完全可接受

3. **时间戳保证同步**
   - 每个数据包带有远程时间戳
   - 后期分析可以精确对齐
   - 不依赖传输实时性
